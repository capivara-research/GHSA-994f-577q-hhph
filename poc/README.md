# Safe reproduction guide

## Prerequisites

- a disposable local TypeMill installation;
- an affected release earlier than `2.27.0` for the vulnerable test;
- a contributor account allowed to upload and publish SVG media; and
- an administrator test account in a separate browser profile.

Do not use a production installation. The included payload is harmless, but the test demonstrates a stored same-origin script-execution condition.

## 1. Check the source without sending requests

Run the checker against a local TypeMill checkout:

```bash
python3 poc/check_source.py /path/to/typemill
```

The script reads `system/typemill/Models/SvgSanitizer.php` and reports whether the security controls introduced by the fix are present. It does not modify the checkout.

Example comparison:

```bash
git clone https://github.com/typemill/typemill.git
cd typemill

git checkout e7b329dc5c4844dd746372449f1b2521456e6aa8
python3 /path/to/GHSA-994f-577q-hhph/poc/check_source.py .

git checkout v2.27.0
python3 /path/to/GHSA-994f-577q-hhph/poc/check_source.py .
```

The first revision is the parent of the upstream security commit. The tag is the fixed release.

## 2. Reproduce the stored XSS safely

1. Sign in to the disposable affected installation as a contributor.
2. Confirm that **Allow svg** is enabled.
3. Upload [`payload.svg`](payload.svg) through the normal media upload workflow and publish it.
4. Copy the direct **Live**, **Original**, or **Thumb** SVG URL generated by TypeMill.
5. In the separate administrator test profile, sign in and open that direct URL.
6. Observe the rendered text.

On an affected release and a browser with SVG XSLT support, the text changes to:

```text
PoC successful: JavaScript executed in the SVG document origin.
```

The transformed document also receives the attribute `data-poc="executed"`. The payload makes no network request and does not access session data.

Repeat the test on TypeMill `2.27.0` or later. The processing instruction must not survive sanitization, so the JavaScript marker must not execute.

## Troubleshooting

- If the vulnerable release shows no transformed output, inspect the stored SVG source to confirm whether the `xml-stylesheet` instruction survived. The browser may have XSLT disabled.
- Open the direct SVG resource, not an HTML page embedding it as an `<img>`; embedded-image scripting is restricted by browsers.
- Compare the exact stored response body and `Content-Type`. The vulnerable condition relies on the stored instruction being served as `image/svg+xml` from the application origin.
